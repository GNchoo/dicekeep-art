# Dicekeep 캐주얼 아트 리마스터 실행 계획

기준일: 2026-09-23
기준 리비전: PR #42 병합 커밋 `7585dea`

## 목표

게임 규칙과 전투 감각은 유지하면서 타이틀, 홈, 보드, 타워, 몬스터, 보스, UI 아이콘과 전투 효과를 하나의 **밝은 장난감 성채 판타지**로 통일한다. 특정 게임의 그림체를 복제하지 않고, 작은 휴대폰 화면에서 한눈에 읽히는 Dicekeep 고유 규칙으로 제작한다.

출시 화면에서 다음 인상이 동시에 나와야 한다.

- 배경은 넓고 단순한 면으로 물러나며 길, 타워 자리와 진행 방향이 먼저 보인다.
- 타워는 주사위 눈과 역할이 실루엣·주색·포구 형태로 구분된다. `★20` 같은 수치는 UI에서 선명하게 유지하고 이미지 안에는 글자를 굽지 않는다.
- 적과 보스는 둥글고 완전한 전신, 명확한 얼굴과 장비, 정확한 이동 유형을 갖는다. 상체 변형 필터, 역관절, 지상 유닛의 부유는 허용하지 않는다.
- 발사 섬광, 투사체, 꼬리, 명중 효과가 한 계열로 이어져 공격의 시작과 결과를 읽을 수 있다. 타워 몸체는 기존처럼 안정적으로 유지한다.
- 홈·덱·출석·우편·성장 패스는 같은 아이콘 조형과 패널 규칙을 쓰며, 보상 수령과 주요 행동이 가장 먼저 보인다.

## 현재 기준

`art-manifest.json`과 `npm run build:www`의 기준값이다.

| 항목 | 파일 | 용량 |
|---|---:|---:|
| 전체 추적 아트 | 2,283 | 358,228,092 B |
| 모바일 빌드 포함 아트 | 2,186 | 328,007,789 B (312.8 MiB) |
| 런타임 원본 | 797 | 106,844,540 B |
| 방향·보행 등 파생본 | 1,389 | 221,163,249 B |
| 보존용·미사용 레거시 | 96 | 28,953,031 B |
| 현재 `www` 전체 | 2,261 | 342,840 KB |

자동 생성 잡은 현재 **키아트 2종과 인피니티 W1~10**만 다룬다. 환경, 타워, 기본 적·보스, UI, VFX, W11 이후에는 대량 생성 전에 잡 생성기와 계약 테스트를 먼저 추가한다.

모바일 빌드에서 제외된 97개는 과거 전체 맵 배경 90개, 현재 쓰지 않는 타워 공격 시트 6개, UI 원본 시트 1개다. 다시 연결하기 전에는 재생성하지 않는다.

## 고정 아트 규칙

모든 실행 프롬프트는 `tools/art-style.json`을 기준으로 한다.

- 큰 둥근 실루엣, 따뜻한 짙은 회색 외곽선, 내부선은 그보다 얇게 사용한다.
- 밝지만 통제된 팔레트와 좌상단 단일 광원, 2단계 무광 셀 명암을 사용한다.
- 재질의 미세한 흠집과 붓 질감은 줄이고 얼굴, 무기, 포구, 날개와 다리를 먼저 읽히게 한다.
- 캐릭터는 실제 표시 높이 42~96px에서도 얼굴·장비·이동 유형이 구별돼야 한다.
- 투명 오브젝트는 발밑 위치와 중심축을 고정한다. 프레임마다 몸 크기, 바닥선이나 무게중심이 출렁이면 불합격이다.
- UI 글자와 숫자는 HTML/CSS로 렌더한다. 생성 이미지에는 글자, 숫자, 로고, 워터마크를 넣지 않는다.
- 유료 스킨은 외형만 바꾸고 전투 판독성과 피격 면적, 능력치, 발사 시점을 기본 스킨과 같게 유지한다.

## 제작 단계

### 0. 파이프라인 기준 확립 — 완료

PR #42에서 중앙 스타일 원본, 고정 모델, 안전한 staging, 실행 manifest, 파일 해시, 이미지 검증, 원자적 승격·복구와 전체 자산 매니페스트를 추가했다. 이후 단계는 이 기준을 우회하지 않는다.

### 1. 생성 범위 확장과 골든 슬라이스

먼저 환경·타워·기본 적/보스·UI/VFX용 잡 생성기와 테스트를 추가한다. 직접 작성한 일회성 프롬프트 묶음을 대량 생성의 원본으로 사용하지 않는다.

한 번의 실제 플레이 화면을 구성할 다음 약 30개 원본만 우선 제작한다.

- 세로·가로 키아트 2개
- 인피니티 아레나 타일 9개
- 1~6눈 기본 타워, ★7·★20 대표, 프리미엄 스킨 대표 1개
- 인간형 지상, 사족 지상, 공중, 땅굴 일반 적과 W10·W100 보스 대표
- 포구 섬광, 탄환/마법탄, 궤적, 명중 효과 대표
- 홈, 덱, 출석, 우편, 성장 패스 대표 아이콘

각 핵심 대상은 이 단계에서만 최대 2개 후보를 만들고 비교한다. 스타일을 확정한 뒤에는 기본 1회 생성과 불합격 항목 1회 재시도로 제한한다. 실행 manifest에서 최초 승인률과 재시도율을 기록한 뒤 전체 비용을 산정한다.

**종료 조건**

- 320×640, 390×844, 1280×900 실제 게임 전후 화면을 나란히 검수한다.
- 배경보다 타워·적·투사체가 먼저 보이고, 축소 화면에서도 각 역할을 구별한다.
- 잘림, 불필요한 글자, 알파 잔상, 피벗 변화, 상체 울렁임, 역관절, 이동 유형 오류가 없다.
- 기존 전투 수치와 공격 시점, 보상·구매 로직은 픽셀 변경 전후에 같다.
- 골든 슬라이스가 승인되기 전에는 같은 계열을 대량 생성하지 않는다.

### 2. 첫인상 영역 교체

플레이어가 매번 보는 순서로 타이틀·홈·덱·보상 UI, 현재 사용하는 타일 24개, VFX 22개를 교체한다. 출석·우편·성장 패스의 기존 고세부 묘사 아이콘도 같은 셀 명암과 외곽선 규칙으로 다시 맞춘다.

이 단계에서 시작 로더를 화면별 로딩으로 나눈다. 현재 `loadAssets()`는 `SRCS` 전체를 한 번에 요청하므로, 타이틀/홈, 선택한 모드, 현재·다음 웨이브, 선택한 스킨 순으로 필요한 파일만 읽도록 바꾼다. 이미지가 바뀐 뒤가 아니라 대량 자산 승격 전에 적용한다.

### 3. 타워와 공격 피드백

모바일 포함 타워 원본 104개를 기본 타워 → ★ 진화 → 무료 스킨 → 유료 스킨 순으로 교체한다.

- 기본 스킨 30개
- ★7~★20 진화 14개
- 스킨 60개
- 기존에 연결되지 않은 공격 시트 6개는 제외

타워별 색 계열을 포구 섬광, 투사체, 궤적과 명중 효과까지 이어 준다. 공격 시 타워 원화 자체를 늘이거나 몸통을 변형하지 않는다. 유료 스킨의 실루엣과 효과 밝기는 기본 스킨보다 전투 정보를 더 잘 보이게 만들지 않는다.

### 4. 기본 캠페인 적과 보스

원본 500적·100보스를 플레이 노출 순서에 따라 스테이지 묶음으로 교체한다. 첫 배치는 초반과 판독 위험이 큰 공중·땅굴·인간형, 스테이지 50 보스를 우선한다. 이후 배치는 한 번에 최대 20개 원본으로 제한한다.

원본이 승인된 뒤에만 걷기 시트와 방향별 파일을 만든다. 프레임을 각각 독립 생성하지 않고 같은 원본과 기존 리그를 사용해 정체성, 관절과 장비를 보존한다.

### 5. 인피니티 W1~101

W1~10은 기존 자동 잡을 새 스타일로 검증하고, W11~101은 `tools/inf-roster.json`에서 10웨이브 단위 잡을 생성하도록 확장한다. 각 단위는 원본 승인 → 측면·정면·후면 정지컷 → 지상 8프레임/비행·부유 4프레임 → 실제 런타임 검수 순으로 진행한다.

W100은 지상 보스 판정과 접지, W101 경계 전환을 별도 회귀 항목으로 유지한다.

### 6. 극한 W102~202

인피니티에서 승인된 조형, 리그와 배치 도구를 그대로 사용해 W102~202를 10웨이브 단위로 진행한다. 기존 극한 파생 자산은 원본 승인 전에는 다시 만들지 않는다. W201·W202의 외형 구별, 이동 유형과 202/203 반복 경계를 별도 검수한다.

### 7. 압축·패키징·출시 검수

알파가 필요한 파일만 투명 형식으로 남기고, 시각 차이가 없는 WebP 변환과 실제 표시 크기에 맞춘 해상도를 적용한다. 일반 유닛 런타임 셀은 256px을 기본으로 하고, 보스는 실제 표시 크기에 따라 384~512px까지만 허용한다.

출시 목표는 다음과 같다.

| 항목 | 목표 |
|---|---:|
| 로비 상호작용 전 이미지 전송 | 10 MiB 이하, 80요청 이하 |
| 첫 전투 진입까지 누적 이미지 | 30 MiB 이하 |
| 전체 활성 아트 디코드 메모리 | 128 MiB 이하 |
| 방향 자산 캐시 | 기존 96 MiB 상한 유지 |
| `www` 전체 | 200 MiB 이하 |
| 모바일 포함 아트 | 180 MiB 이하 |
| 기준 휴대폰 전투 프레임 | p95 16.7ms 이하, 현 기준 대비 10% 초과 퇴행 없음 |

총량 목표를 해상도 조정과 WebP로 달성하지 못하면 인피니티·극한 방향 자산을 선택 다운로드 묶음으로 분리한다. 이 경우 빈 스프라이트 없이 다음 웨이브를 미리 받으며 오프라인 실패 시 같은 캐릭터의 축소 fallback을 사용한다.

## 배치별 승인 절차

1. 잡을 생성하고 `--dry`로 모델, 스타일 버전, 최종 프롬프트와 출력 경로를 확인한다.
2. `gen/`에 생성하고 입력·참조·출력 해시가 담긴 실행 manifest를 보존한다.
3. 원본 크기, 42~96px 축소본, 실제 게임 전후 캡처를 한 비교판으로 만든다.
4. 시각 승인 후에만 런타임 경로로 승격하고 `art-manifest.json`을 다시 만든다.
5. 범주별 회귀 검사와 빌드가 모두 통과한 배치만 PR로 `main`에 병합한다.
6. 문제가 생기면 해당 배치 커밋과 manifest 해시로 자산 단위 롤백한다.

공통 검사는 다음과 같다.

```powershell
npm run test:art-pipeline
npm run build:www
```

캐릭터·보스 배치는 `npm run test:biped-knees`, `npm run test:combat-motion`, `npm run test:boss-locomotion`을 추가한다. UI 배치는 `npm run test:home`, `npm run test:rewards-visual`을 추가한다. 방향 자산은 세 방향, 모든 애니메이션 위상, 두 휴대폰 크기에서 404와 실행 오류 0건을 확인한다.

## 바로 이어서 할 작업

1. 타워·환경·UI/VFX 잡 생성기와 `golden-slice.json` 계약을 추가한다.
2. 시작 로더 요청 수·바이트·디코드 메모리 기준을 자동 측정하는 테스트를 추가한다.
3. 골든 슬라이스 후보를 staging에 만들고 모바일 인게임 비교판을 생성한다.
4. 승인된 스타일과 실제 재시도율로 남은 범주별 생성량과 비용을 확정한다.
5. 첫인상 영역부터 작은 PR로 순차 병합한다.
